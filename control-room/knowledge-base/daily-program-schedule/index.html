Daily Program Schedule

Operating and technical reference for the Vancouver Aquarium® Program Schedule Admin, which prepares date-specific schedules for Guest Services and wayfinding signage.

Overview

The Daily Program Schedule CMS lets authorised staff create, review, reuse and publish program schedules for a specific calendar date. Each date can have a separate draft record and live record. The editor works from the draft; the digital signs read only the live schedule for the current Vancouver date.

Supabase Auth → Program Schedule Admin → program_schedule_sets → Guest Services + Wayfinding
Two database tables support the system: program_schedule_sets stores date-specific draft/live schedules, while program_location_styles supplies the recognised location names and display colours used by the editor and signs.

Staff Quick Start

For a normal one-day schedule update, use this sequence. It keeps the saved draft aligned with the version that becomes live and reduces the chance of accidentally propagating unsaved or stale schedule data.

Sign in.

Use an authorised VAQ schedule editor account. If a valid Supabase session already exists, the administration interface opens automatically.

Choose the Schedule Date and select Load Date.

The editor loads the active location styles, the live schedule for that date (if one exists), and the saved draft for that date (if one exists).

Create a draft if the date does not have one.

Choose Create Empty Draft. A date must have a draft record before programs can be edited in the schedule table.

Add, duplicate or edit the program rows.

Each program needs a title, recognised location, start time and end time. Mark a row Cancelled when it should remain in the schedule record but not appear on signage.

Add an Internal Day Note if useful.

The Day Note is stored with the schedule for staff context and identification. It is not currently rendered on the guest-facing signs.

Choose Validate Schedule.

Fix every validation error before saving or publishing. The editor checks IDs, required fields, recognised locations and the start/end time relationship.

Choose Save Draft.

This writes the current program rows and Day Note back to the selected date's draft record.

Review the Schedule Summary and Currently Live preview.

The summary helps compare the edited draft with the date's already-published live schedule, if one exists.

Choose Publish Live.

After confirmation, the current validated page state is written to that date's live record.

Verify the live signs.

Both schedule display families poll Supabase every 25 seconds, so a successful publish should normally become visible shortly afterward when that date is the current Vancouver date.

Recommended routine: Validate → Save Draft → Publish Live.
Publish Live uses the currently edited page values, even if those edits have not first been saved back to the draft database row. Saving first keeps the draft and live versions aligned.
Loading or reloading data can discard unsaved browser edits. Use Save Draft before changing dates, choosing Load Date, or choosing Reload Data whenever you need to preserve the work currently shown on the page.

Editing Programs

Create Empty Draft

Creates a new draft schedule record for the selected date with an empty program list, an empty Day Note and America/Vancouver as its timezone. It will not create a second draft when one already exists.

Add Program

Adds a new unsaved row. A new row begins with a generated internal ID, a 15-minute default duration and a starting time based on the latest program start already in the editor (or 9:00 a.m. when the draft is empty).

Duplicate

Copies an existing row and gives the duplicate a new internal entry ID. The duplicated row remains an unsaved browser edit until Save Draft is chosen.

Delete

Uses a two-click confirmation. The second click must occur within approximately four seconds. The deletion is only local until the draft is saved.

Cancelled

Keeps the program in the schedule record but marks it is_cancelled = true. Guest-facing displays filter cancelled programs out completely.

Validate Schedule

Sorts the current entries by start time and reports validation errors. Validation alone does not save anything to Supabase.

Save Draft

Validates, sorts and writes the current program rows and Day Note to the loaded draft record. Saving is blocked while validation errors remain.

Publish Live

Validates the current page state, asks for confirmation, then upserts a live record for the selected date. It can replace an existing live schedule for that same date.

Validation rules

  • Every entry must have an internal entry ID.
  • Internal entry IDs must not be duplicated within the schedule.
  • Program Title is required.
  • Location is required and must match an active program_location_styles record.
  • Start Time is required and must be valid.
  • End Time is required and must be valid.
  • End Time must be later than Start Time.
  • Cancelled rows are still part of validation even though the public signs do not render them.
The editor's time controls present minutes in five-minute increments. Multiple programs can share the same start time; the current validation logic does not prohibit overlapping or simultaneous programs.

Schedule Tools

The Schedule Tools accordion exists to reduce repetitive data entry, but these commands can affect several date records at once. Review source and target dates carefully before confirming them.

Copy Tool

Copy from Date

Copies another date into the currently selected date's draft. The source lookup prefers that date's draft; if no draft exists, it falls back to that date's live schedule. The target draft is created if needed, then overwritten after confirmation. The target's live record is not changed.

Copy Tool

Copy Same Weekday from Last Week

Automatically uses the date seven days before the selected target date and then runs the normal Copy from Date process, including source priority and overwrite confirmation.

Planning Tool

Repeat Weekly Until Date

Takes the current validated editor state and copies it into weekly target dates. Existing target drafts are skipped by default. Enabling Overwrite existing drafts allows those draft records to be replaced. Live records are not published or replaced by this tool.

Publishing Tool

Publish All Drafts

Finds populated saved drafts that do not already have a live record. Empty drafts are skipped. Every populated candidate must pass validation before the batch can run. Existing live schedules are deliberately never overwritten.

Copy from Date prefers a source draft over a source live schedule. A stale or incorrect draft can therefore be copied even when the same source date has a different, correct live version. Before using Copy or Last Week, confirm that the source draft is genuinely the version you intend to reuse.
Save before Repeat Weekly. Weekly Repeat uses the current validated page state, so it can propagate edits that have not yet been saved back to the source date's draft. Saving first creates a clearer, recoverable source record.
Publish All Drafts is for first-time publication of prepared dates. If a date already has a live record, that date is excluded from the batch even when its draft has newer changes. To update an already-live date, load that date and use the normal Publish Live action.

Publishing Rules

Single-date Publish Live

Can create or replace the live record for the selected date. It publishes the current in-browser editor state after validation and confirmation.

Publish All Drafts

Reads saved draft rows from Supabase. It does not use unsaved browser edits and it does not overwrite dates that already have live records.

Future live schedules

A live record can exist before its date arrives. The guest-facing signs query only the live row whose schedule_date matches the current date in America/Vancouver.

Day Note

Travels with draft/live schedule records for staff reference but is not currently rendered by the guest-facing full or wayfinding schedule displays.

Guest-Facing Displays

The same published schedule feeds two current display families. Both use America/Vancouver to determine today's date, query the matching live schedule, query active location styles, remove cancelled programs, and refresh database data every 25 seconds.

Full Guest Services schedule — 1920 × 810 gs-1-2_daily-program-schedule/program-schedule-full/

Displays up to 10 remaining program entries in two columns, five positions per column.

Wayfinding schedule — 1080 × 480 wf_daily-program-schedule/

Compact sibling display using the same database data, showing up to six remaining entries in two columns, three positions per column.

Live refresh 25000 ms

Both displays poll for changed schedule/location data every 25 seconds. Time-driven queue changes also occur locally around program start-time boundaries.

What a program tile shows Title · Start Time · Location

Location colour comes from program_location_styles.hex_color. The nearest upcoming/start-time group receives additional visual emphasis.

Automatic display behaviour

  • Cancelled entries are removed before rendering.
  • Entries whose end time has passed are excluded when the visible queue is recalculated.
  • Programs are sorted by start time.
  • The public queue displays only a limited number of remaining entries at once.
  • If no live schedule exists for today, a friendly “still setting up today’s schedule” status is shown.
  • When no program entries remain visible, the display shows a “today’s programs have finished” message.

Data & Supabase

The August 25, 2026 schema snapshot identifies two application tables in the public schema. At the time of that snapshot, program_schedule_sets contained 54 rows and program_location_styles contained 21 rows.

public.program_schedule_sets

Column Purpose in this CMS Operational meaning
id UUID primary key for a schedule record. Identifies the individual draft/live row.
schedule_date Date the schedule belongs to. Public signs request today's Vancouver date.
mode Schedule state: draft or live. Editor plans in draft; signs read live.
timezone_name Timezone metadata; default is America/Vancouver. Keeps schedule/date interpretation anchored to Vancouver.
entries_json JSON array containing all program rows for the date. Main editable schedule content.
day_note Optional internal note. Staff context only; not currently guest-facing.
saved_at Save-related timestamp. Used for schedule status/history context.
published_at Publish timestamp. Shown by the admin when describing the live schedule.
created_at / updated_at Record lifecycle timestamps. Technical maintenance and change detection.

Program entry JSON shape

The current editor creates and saves entry objects with the following working shape. The description property exists in the object model but is currently cleared during sanitisation and is not presented as an editable field. 

{
  "id": "entry_...",
  "title": "Program title",
  "location_key": "location-key",
  "start_time": "10:00",
  "end_time": "10:15",
  "description": "",
  "is_cancelled": false
}

Infrastructure currently not used for schedule content

Supabase Storage is provisioned but the supplied schema reports zero buckets and zero objects. Supabase Realtime infrastructure also exists, but the current signage implementation uses timed database polling rather than a Realtime subscription.

Location Styles

public.program_location_styles is the shared location reference table. It is not edited by the Program Schedule Admin itself; the admin reads active records and uses them to build the Location dropdown and validate schedule rows.

Column Current role
location_key Unique machine-readable location identifier stored in each program entry.
display_name Human-readable location name shown in the admin and public program meta line.
hex_color Six-digit location colour used to colour program tiles.
icon_path Schema field available for icon metadata. The current full and wayfinding renderers derive their SVG icon file path from location_key rather than reading this field.
sort_order Controls location ordering in the admin dropdown.
is_active Only active locations are loaded by the editor/displays. A program using an inactive or unknown location key will fail current editor validation.
Location key and icon filename are operationally linked in the current displays. Because the renderers construct SVG paths from location_key, changing a key without providing the matching icon file can break that program's icon even if the database icon_path field contains something else.

Authentication & Security

The administration interface uses Supabase Auth email/password sessions. On startup it calls auth.getSession(); authenticated staff see the CMS, while unauthenticated visitors see the Sign In panel.

  • Both application tables have Row Level Security (RLS) enabled.
  • The schema snapshot does not include the individual RLS policy definitions because policy inspection was not authorised in that session.
  • The public signage pages use the project's public/publishable Supabase client and depend on permitted read access to today's live schedule and active location styles.
  • The schedule table records timestamps but the supplied app schema does not include an editor/user ID field that attributes each save or publish to a specific staff account.
Do not place credentials in the Control Room or knowledge base. Passwords, service-role keys, private tokens and other secrets must never be committed to this public GitHub Pages repository.
Future documentation improvement: archive the exact RLS policy definitions for both public application tables in a secure maintenance record. The current schema establishes that RLS is enabled, but not the exact select/update/insert rules.

Supabase client

The admin and signage pages use @supabase/supabase-js@2. The CMS uses authenticated session operations; the signage pages perform public reads.

Schedule loading

The admin loads the selected date's draft and live records separately, plus all active location styles ordered by sort_order.

Saving

Save Draft updates the currently loaded draft row by ID and writes the sanitised entries_json, trimmed day_note and a new saved_at value.

Single-date publishing

Publish Live upserts a live record using the conflict target schedule_date,mode. This means the application expects that date/mode combination to behave as a unique schedule state. Publishing writes the current editor entries and Day Note along with save/publish timestamps.

Copy source priority

Copy from Date queries the source date's draft first. Only when no draft exists does it query that source date's live record.

Sorting

Editable entries are sorted by start time, with title used as a secondary ordering rule when start times are equal. Batch publishing also sorts saved draft entries before writing live records.

Public display queries

Each display queries active program_location_styles and the program_schedule_sets row where schedule_date is today's Vancouver date and mode = "live".

Polling and queue timing

Database content is rechecked every 25 seconds. If the fetched schedule/location payload changes, the display reapplies it. Separately, the visible program queue is recalculated at program start-time and five-minutes-after-start boundaries; end times are used when deciding which entries remain eligible whenever that queue recalculation occurs.

Public display sizes

  • Full Guest Services schedule: 1920 × 810, maximum 10 visible entries.
  • Wayfinding schedule: 1080 × 480, maximum 6 visible entries.

Troubleshooting

No draft exists for the selected date.

Choose Create Empty Draft or use a Copy tool to prepare a target draft. Programs cannot be edited until a draft row exists.

Save Draft or Publish Live is blocked.

Run Validate Schedule and inspect the row-level errors. Common causes are a blank title, missing location, inactive/unrecognised location key, invalid time, or an end time that is not later than the start time.

Edits disappeared after loading/reloading.

Changes in the table remain browser-side until Save Draft succeeds. Loading database data again restores the saved draft state and can discard unsaved edits.

The live schedule contains changes that are not in the saved draft.

Publish Live can publish current unsaved page edits. Recreate/verify the intended editor state, Save Draft, then Publish Live again if the two records should match.

Copy from Last Week produced unexpected content.

Remember that Copy prefers the source date's draft over its live record. Inspect the source draft before copying when there is any possibility that an old or test draft remains.

Repeat Weekly skipped some dates.

Existing draft rows are skipped unless Overwrite existing drafts is enabled. The completion message reports Created, Updated, Skipped and Error counts.

Publish All Drafts did not republish a changed date.

The batch tool intentionally excludes every date that already has a live row. Use the normal single-date Publish Live command to replace an existing live schedule.

Publish All Drafts is completely blocked.

If any populated unpublished draft fails validation, the entire batch is blocked until those date(s) are corrected. Empty drafts are skipped rather than published.

A cancelled program still appears in the admin.

That is expected. Cancelled programs remain stored in the schedule for staff reference, but the guest-facing displays filter them out.

The public sign says today's schedule is still being set up.

The display did not find a live schedule for today's Vancouver date. Verify the selected date, confirm that it was actually published live, and then verify Supabase read access if the live row exists.

A program has the correct location name/colour but its icon is missing.

Verify that an SVG file matching the program's location_key exists in the expected shared icons directory. The current display code derives the icon filename from that key.

Maintenance

Review this documentation whenever any of the following changes:

  • The structure of entries_json changes.
  • The draft/live model or schedule uniqueness rules change.
  • Copy, Repeat Weekly or Publish All Drafts behaviour changes.
  • Validation rules change.
  • The program_location_styles schema or active location keys change.
  • Location icon paths are decoupled from location_key.
  • The full or wayfinding display dimensions/page sizes change.
  • The 25-second database polling interval changes.
  • Supabase Auth or RLS policies change.
  • Another signage family begins consuming this same live schedule data.

Current documentation limitations

  • The supplied schema confirms table-level RLS but did not include the exact RLS policy definitions.
  • The schema summary does not describe an application-level audit trail tying individual schedule saves/publishes to a specific Auth user.
  • The schema describes icon_path, but the current inspected display implementations derive SVG paths from location_key instead.
