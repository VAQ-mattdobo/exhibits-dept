Overview

The Daily Pricing Builder is the staff-facing editor used to prepare and publish General Admission pricing for the Vancouver Aquarium Admissions digital signage. Staff edit four pricing rows plus shared tax and footer text, compare a draft preview with the currently published live version, and then choose when the new information should become guest-facing.

Supabase Auth → General Admissions Screen Editor → pricing_sets → Admissions pricing displays
Two separate states are maintained: a saved draft row and a published live row. The guest-facing displays read only the live row.

Staff Quick Start

For ordinary pricing updates, use this sequence. It keeps the saved draft and published live state aligned and gives staff an opportunity to catch formatting errors before anything reaches the guest-facing screens.

Sign in.

Use an authorised Exhibits Department login. The editor checks for an existing Supabase session first; if no session exists, the login screen is shown.

Review the loaded Draft and Live states.

The editor loads both database rows. The form is populated from the saved draft, while the separate Live Preview shows what is currently published.

Edit the four pricing rows.

Each row has a Label, Age and Price. The form also includes shared Tax Text and a Footer Note.

Choose Preview Draft.

This validates the form and updates only the local Draft Preview. It does not write anything to Supabase.

Choose Save Draft.

This writes the current form values to the database row where mode = "draft" and updates the saved timestamp. Guest-facing signage is not changed.

Choose Publish Live.

After a confirmation prompt, the current form values are written to the database row where mode = "live". The live preview then reloads.

Verify the guest-facing display.

The pricing displays poll Supabase every 60 seconds, so a successful publish should normally appear within approximately one minute.

Sign out when finished.

The Sign Out button ends the Supabase Auth session and returns the page to the login state.

Recommended publishing sequence: Preview Draft → Save Draft → Publish Live.
In the current implementation, Publish Live does not also save the draft database row. If staff edit values and publish without first choosing Save Draft, the published live values can be newer than the saved draft values.

What Each Button Does

Preview Draft

Reads the values currently entered in the form, validates them and refreshes the Draft Preview. Nothing is written to Supabase. This is safe for experimenting with wording and layout.

Save Draft

Validates the form and updates only the draft pricing record. It also updates saved_at and updated_at. This does not change the guest-facing signs.

Publish Live

Validates the form, asks for confirmation, then updates only the live pricing record. It updates published_at and updated_at, then reloads the Live Preview from Supabase.

Reset Draft

Replaces the form and Draft Preview with the editor's built-in default sample pricing locally only. It does not automatically write those defaults to the database.

Sign Out

Ends the current Supabase Auth session, clears the login fields and returns to the login screen.

Reset Draft is not an “undo to last saved draft” command. If Reset Draft is clicked accidentally and nothing has been saved or published afterward, refreshing/reopening the page will reload the actual saved draft row from Supabase.

→
Authenticated browser session The editor uses the logged-in session for database operations.
2. Editor /admin.html
→
Supabase table public.pricing_sets contains separate draft and live records.
3. Publish Current form values are written to mode = "live".
→
Guest-facing signage Display pages query only the live record and render its pricing content.
4. Ongoing refresh Display pages poll every 60 seconds.
→
Automatic update New live pricing appears without manually editing the display HTML.

This is a deliberately small architecture. Supabase stores the editable content, the CMS controls when draft content becomes live, and the guest-facing web pages independently read the published state.

Guest-Facing Displays

The same published pricing data is used by more than one Admissions layout. The visual dimensions and typography differ, but both display variants query the same pricing_sets table and select the record where mode = "live".

Slim pricing content — 1152 × 810 ga-4-2b_pricing-content-slim/index.html

Narrower live layout using the same database fields, with adjusted spacing and type sizes for the 1152-pixel-wide container.

Live data behaviour mode = "live" · refresh interval: 60000 ms

Each display loads the live pricing immediately on startup and then requests it again every 60 seconds.

If the display cannot load the live row, its fallback state shows “Pricing Unavailable” and “Please check back shortly.” This usually means the live query failed or no valid live pricing record was returned.

Data & Supabase

As of the schema snapshot generated August 25, 2026, the application has one business-data table: public.pricing_sets. The table contains two rows, representing the draft and live pricing states.

Column Purpose in this CMS Used by
id Identity primary key. Database structure.
mode Unique state identifier. The application uses draft and live. Editor and displays.
rows_json JSON array containing the four pricing rows. Each application row uses label, age and price. Editor, previews and displays.
tax_text Shared tax text displayed beside each price. Editor, previews and displays.
footer_note Shared footnote/footer text shown at the bottom of the pricing content. Editor, previews and displays.
updated_at General record-update timestamp. Database maintenance.
saved_at Timestamp updated when Save Draft succeeds. Draft status in editor.
published_at Timestamp updated when Publish Live succeeds. Live status in editor.

What is not required for this CMS today

Supabase Storage and Realtime infrastructure exist in the project, but the supplied schema snapshot shows no Storage objects/buckets in use and no active Realtime data. The pricing signs use ordinary database queries plus timed polling rather than a Realtime subscription.

Simple data model: pricing_sets currently has no documented foreign-key dependencies. This makes the pricing system relatively easy to understand and maintain compared with the more complex schedule-based CMS applications.

Authentication & Security

Supabase Auth handles staff identity and browser sessions. The editor checks auth.getSession() when it starts, signs staff in with email/password authentication, and signs out through Supabase Auth.

  • The editor requires an authenticated session before the administration interface is shown.
  • The browser uses the project's public/publishable Supabase client configuration.
  • public.pricing_sets has Row Level Security (RLS) enabled.
  • The supplied schema summary does not include the actual RLS policy definitions.
  • The business table has no documented foreign key linking a pricing edit to a specific Auth user.
Do not place credentials in the Control Room or knowledge base. Passwords, private tokens, service-role keys and other secrets must never be documented in this public GitHub Pages repository.
Future documentation improvement: export and archive the explicit RLS policies for public.pricing_sets. The current schema confirms that RLS is enabled, but does not establish exactly which authenticated roles can select or update each row.

Technical Reference

Editor entry point

/admin.html

Supabase client library

The editor and displays load @supabase/supabase-js@2 from jsDelivr.

Editor startup

On page load, the editor checks the current Auth session. Authenticated users proceed to the admin app, which loads the saved draft and published live rows separately.

Validation rules

  • All four labels are required.
  • All four age-text fields are required.
  • All four prices are required.
  • Price format must begin with $ and include exactly two decimal places, such as $50.46.
  • Tax Text is required.
  • Footer Note is required.
  • Preview, Save and Publish are blocked until validation succeeds.

Save Draft database action

Updates rows_json, tax_text, footer_note, saved_at and updated_at on the record where mode = "draft".

Publish Live database action

Updates rows_json, tax_text, footer_note, published_at and updated_at on the record where mode = "live".

Display query

The Admissions pricing displays request rows_json, tax_text and footer_note from the live pricing record. They do not read the draft record.

Refresh behaviour

Live pricing is loaded immediately and then refreshed every 60000 ms (60 seconds).

Troubleshooting

The editor only shows the login screen.

Confirm the staff user is signing in with an authorised Supabase Auth account. If sign-in fails, the editor displays the Supabase error message.

Preview Draft will not update.

Check the validation message. Every field is required, and each price must use the expected format such as $50.46.

The draft preview looks correct, but reopening the editor loses the changes.

Preview Draft is local only. Choose Save Draft to write the changes to Supabase.

The live signs changed, but the saved draft still contains older values.

Publish Live and Save Draft are separate operations. Use Save Draft before publishing when you want the saved draft to match the live state.

Reset Draft replaced the form with unfamiliar values.

Reset Draft loads the built-in default sample data. If those values have not been saved or published, reload the page to retrieve the actual saved draft from Supabase.

Publish succeeded, but the physical sign has not changed yet.

Allow up to approximately 60 seconds for the display's next database poll. If it remains unchanged, verify the web display itself and the Kuusoft channel assignment.

The sign says “Pricing Unavailable.”

The live display could not retrieve a valid live pricing row. Check network access, the Supabase project, the live record, and any relevant RLS/read policy.

Maintenance

Review this documentation whenever any of the following changes:

  • The four pricing-row structure or shared text fields change.
  • The pricing_sets schema changes.
  • Supabase Auth or RLS policies change.
  • The editor's Save Draft / Publish Live behaviour changes.
  • The guest-facing pricing display paths or dimensions change.
  • The 60-second polling interval changes.
  • A new Admissions pricing layout begins using this same live data.
